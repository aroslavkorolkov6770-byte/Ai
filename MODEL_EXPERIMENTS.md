Все эксперименты выполнены локально, без готовых открытых весов. Loss можно напрямую сравнивать только у версий с одинаковой токенизацией. Между разными токенизаторами главным ориентиром служит полнотекстовое сходство ответа на одном фиксированном наборе.

## Вывод

Собственный BPE-словарь из 512 токенов сократил среднюю длину train-текста с `48.48` до `24.68` токена, то есть на `49.09%`, без ошибок обратного восстановления. Полнотекстовое сходство выросло с `0.2776` у посимвольного `v0.7` до `0.3575` у 12-эпохового `v0.8` и до `0.4870` у 20-эпохового `v0.9`.

`v0.9` формирует более короткие и тематически близкие фрагменты, но neural-only всё ещё дал `0/20` точных ответов, а три ручных follow-up-теста — `0/3`. Поэтому версия выбрана лучшей технической основой, но не считается моделью приемлемого разговорного качества. Следующий основной шаг — привести датасет к нескольким чётким темам и единому стилю ответа.

Все предыдущие кандидаты и резервные копии сохранены в `model_artifacts/versions/`. Активная копия `v0.9` дополнительно сохранена как `gru-bpe-v0.9-20epochs-selected`.

## LMS-контекстная модель v2.0

| Версия | Данные | Архитектура | Validation | Независимый test | Решение |
|---|---|---|---:|---:|---|
| `lms-context-policy-v2.0` | 22 642 train / 2 779 validation / 2 812 строгий test из 60 000 исходных строк | Собственная hash-feature MLP policy + fact-ranker, 10 LMS-задач, структурный guard | accuracy `1.0`, macro recall `1.0`, 0 ошибок | `2812/2812`, 0 неверных, 0 утечек контекста | Принята и установлена |

В отличие от GRU-кандидатов, LMS v2.0 не пытается генерировать ответ посимвольно.
Нейросеть выбирает политику, fact-ranker выбирает факт, а безопасный декодер
возвращает полный связный текст из переданного контекста. Это осознанная смена
структуры задачи, а не добавление похожих реплик. Ручная release-регрессия дала
`12/12`; checkpoint SHA-256:
`E0A7A728B37A81B0A27934D4FFFD9687202077AE319983FA9531D867FAAB2A5A`.

Ограничение: модель отвечает по LMS-контексту и не является универсальным
собеседником. Follow-up на LMS-состояниях будет отдельным экспериментом с новым
отложенным набором, чтобы не смешать качество policy-ответа и качество памяти.

## Автоматический локальный LMS-маршрут

Это не новое переобучение checkpoint и не новая метрика `lms-context-policy-v2.0`.
Из уже проверенного импорта построен отдельный `knowledge_index.json`: `23 702`
уникальные контекстные группы и `28 233` уникальные пары «вопрос + контекст».
Индекс не читает поле `system` как инструкцию и не изменяет исходные JSONL.

Новый маршрут `response_mode=auto` сначала использует принятую веб-модель, затем
ищет один безопасный LMS-контекст и передаёт его в существующую LMS-model. После
подтверждённого ответа контекст сохраняется в SQLite только для follow-up того же
диалога. Пользователь не видит переключателя LMS или поля контекста.

Ключевое ограничение датасета остаётся: одинаковый вопрос может соответствовать
разным правилам. Поэтому при нескольких кандидатах индекс возвращает уточнение,
а не самый похожий процент. Отдельные API-регрессии проверяют три свойства:
веб-вопрос продолжает работать в `auto`, естественно написанные детали курса
выбирают подтверждённый контекст, а неоднозначный вопрос не выдаёт одно из
конфликтных чисел.

Следующее улучшение маршрута не заменяло checkpoint и не добавляло похожие
диалоги в обучающие данные. В индексе появились компактные смысловые темы и
сопоставление словоформ названий курсов. Это позволяет обработать обычный
вопрос о результате для зачёта или пересдаче, а также использовать короткий
follow-up после подтверждённого контекста. Регрессии проверяют естественное
название курса, перефразированный проходной результат и перефразированную
пересдачу; полный локальный набор: `71/71`.

## Эксперимент с декодированием

Для проверки альтернативы последовательному выбору добавлен необязательный beam search шириной `3`. Он использует те же локальные веса, BPE-токенизатор и ограничения повторов; это изменение способа генерации, а не новое обучение.

На тех же 28 test-вопросах v1.3 результаты такие:

| Режим | Точных ответов | Среднее сходство | Решение |
|---|---:|---:|---|
| `sample`, `top_k=1` | `0/28` | `0.3092` | Оставлен основным |
| `beam`, ширина `2` | `0/28` | `0.2886` | Не выбран по умолчанию |
| `beam`, ширина `3` | `0/28` | `0.2818` | Не выбран по умолчанию |
| `beam`, ширина `5` | `0/28` | `0.3001` | Не выбран по умолчанию |

Beam search оставлен доступным для отдельных экспериментов через `decoding=beam`, но активный API продолжает использовать `decoding=sample`. Даже лучший из проверенных beam-вариантов уступил обычному режиму на `0.0091`, поэтому текущему узкому GRU+BPE важнее улучшение данных и обучения, чем усложнение поиска токенов.

Кандидат v1.4 с расширенным диалоговым набором дал лучшую validation/test loss и token accuracy, но ухудшил оба внешних benchmark: `0.2961` против `0.3092` на одиночных веб-вопросах и `0.2117` против `0.2261` на follow-up с контекстом. Поэтому loss на маленькой validation-части не используется как единственный критерий принятия.

## Надёжный QA-декодер v2

Вместо дальнейшего увеличения GRU изменена постановка задачи. Собственная MLP выбирает один из 32 смыслов по обученным внутри проекта словесным и символьным признакам. Ответ декодируется целиком, поэтому ошибка внутри произвольной последовательности токенов невозможна.

Точность принятых ответов и доля целых ответов равны 100% в обоих наборах. Отказы по поддерживаемым вопросам учитываются отдельно и не маскируются как успех.

Ранние кандидаты подтвердили, что один общий порог и несколько ручных фраз дают слишком много отказов. Итоговый эксперимент добавил замороженные QA-вероятности, пороги по состояниям, смысловую композицию и контрастное обучение действий над одинаковыми объектами.

| Версия | Данные | Архитектура | Validation | Независимый test | Решение |

Модель не декодирует ответ по токенам. Она решает только вопрос «это обычное

выборка мала и частично синтетична. Поэтому в API есть дополнительные границы:
явные запросы факта и знания не перехватываются conversation-brain, а идут в QA
или интернет. Независимая API-приёмка `8/8` сценариев сохранена в
`evaluation/results/conversation-brain-v1-acceptance/`.

## Web-dialogue-policy v1.0

| Версия | Данные | Архитектура | Validation | Независимый test | Решение |
|---|---|---|---:|---:|---|
| `web-dialogue-policy-v1.0` | `140/30/30` проверенных synthetic seed-записей; только user-реплика и `browse_label` | Собственные признаки → EmbeddingBag → MLP `32→32→5` | accuracy `86.67%`, поиск precision `100%`, recall `75.00%` | accuracy `66.67%`, поиск precision `100%`, recall `58.33%`, 0 ложных поисков | Принята как дополнительный осторожный сигнал |

Это отдельный policy-классификатор, а не генератор и не замена
`internet-router-v1.0`. Пять классов описывают решение вокруг веба:
`must_browse`, `should_browse`, `may_browse`, `must_not_browse` и
`insufficient_context`. API включает поиск только для двух первых классов при
confidence `>= 0.85`, margin `>= 0.30` и coverage `>= 0.20`.

Закрытый test содержит лишь 30 записей, поэтому `66.67%` общей accuracy не
выдаётся за универсальное качество ИИ. Положительный gate выбран по более
узкой и важной метрике: во всех 7 автоматических включениях поиска модель не
создала ложного обращения к сети. Оставшиеся 5 случаев не ломают ответ: их
по-прежнему покрывают явные правила, weather/temporal маршруты,
`internet-router-v1.0` или последующее безопасное уточнение.

Архив прошёл отдельный аудит, однако готовые ответы, system/tool-сообщения,
evidence, ссылки, search queries и архивный Python-код намеренно не попали в
обучение. Подробности: `DIALOGUE_WEB_SEED_AUDIT.md` и
`WEB_DIALOGUE_POLICY_TRAINING_REPORT.md`.
